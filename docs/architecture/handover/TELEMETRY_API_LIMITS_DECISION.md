## 2. 可批准方案（建议；带数值的行均为候选）

下列数值全部标记为 **候选（PENDING_OWNER）**。选定理由是为了给 Owner 一个可签字的明确提案，而不是实施授权。

| 约束 | 候选规则与数值 | 依据 | 批准状态 |
| --- | --- | --- | --- |
| 官方路由 | 正式 Adapter 契约只包含 **POST** `/v1/telemetry/events`。GET 不纳入官方契约，正式验收不得依赖 GET。若过渡期代码仍暂留 GET，必须另审角色门槛、分页与审计，且不得绕过与 POST 相同的身份/授权边界 | 现实现已暴露未文档化 GET，存在绕过与过量读取风险 | 原则建议；**非 APPROVED** |
| 最大请求体字节数 | **候选：65536 字节（64 KiB）**，按未解码的原始请求体计量（含空白）。在解析 JSON 之前计数 | Phase 1 事件应为结构化元数据与短摘要，不应承载附件或完整文件；64 KiB 足以容纳红化后的运行时事件，同时给未红化载荷一个硬上限。若后续证明工具观察经常超限，应改契约而不是静默截断 | **PENDING_OWNER**。确认前不得称为最终批准值 |
| 超限响应 | **413 Payload Too Large**；**禁止截断后部分解析或入库**；响应不回显完整超大体；记录审计与指标 | 截断会导致半截 JSON 被当成成功事件，破坏证据完整性 | 状态码待批 |
| Tenant 维速率限制 | **候选：每个已验证 `auth.tenantId` 平均 20 请求/秒，突发 40 请求/秒，窗口 1 秒**。以已验证认证上下文计，不得用事件体内未验证 `tenantId` 计 | 限制单租户误配置或故障循环打满共享入口；数值偏保守，便于 Phase 1 观察后再调 | **PENDING_OWNER** |
| Service Identity 维速率限制 | **候选：每个已验证 Service Identity（`auth.subjectId` 且 `principalType=service`）平均 10 请求/秒，突发 20 请求/秒，窗口 1 秒**。User 反馈通道如获批，应使用更严且独立的预算（候选：2 请求/秒，突发 5） | 防止单一泄露或被盗凭证打满整租户配额；双维同时生效，任一维触顶即限流 | **PENDING_OWNER** |
| 超限（限流）响应 | **429 Too Many Requests**，响应头 **`Retry-After: 1`**（候选整数秒，按当前 1 秒窗口）。被限流请求不入库。出站侧将 429 视为可重试，但不得在 OpenBot 主执行链上同步阻塞 | 与候选窗口对齐；无批准值前不得宣称生产限流已生效 | **PENDING_OWNER** |
| 未知字段 | **丢弃且不持久化**。不得因「前向兼容」把未声明字段写入 `payload_json`。校验失败的已知字段返回 **400**，不入库。不默认采用「显式扩展袋」 | 当前实现会整对象落库，存在意外 PII 与契约漂移 | 原则建议；**非 APPROVED** |
| PII 检测与服务端 redaction | **必须在服务端执行**。客户端 `redaction.applied` **不得作为已红化证据**，最多作为调用方自报声明写入审计并与服务端结果对照。服务端未完成红化策略（策略名待 Owner 指定）前，不得接受含原文的敏感字段入库。建议：对未通过服务端红化检查的请求返回 400，不入库 | 现实现只检查字段存在，等于信任客户端 | 原则建议；策略细节 **PENDING_OWNER** |
| 幂等键生成 | 由 OpenBot **出站侧**生成稳定键，派生自内部事件身份（例如 `source.system + eventId` 或专用 `evt_…`），**禁止使用 Trace ID** | D-04；避免追踪补造或共享 trace 导致错误合并 | 原则建议；待与 D-04 一并签批 |
| 幂等作用域 | **已验证 Tenant ID + Idempotency Key** 唯一。跨租户相同键不得互相去重或串桶 | 与现有 UNIQUE 事实对齐 | 待作为正式契约签批 |
| 幂等保留期 | **候选：24 小时**（从首次成功接受起算）。保留期内重复提交按「同一键」处理；超过保留期后同一键再提交视为新冲突或新事件的规则必须由 Owner 二选一。本方案默认建议：超期后同一键若载荷指纹不同则 **409 Conflict**，若完全相同则仍返回幂等成功，以避免延迟重放被当成新业务，但须在签批时确认 | 现实现无 TTL。24 小时覆盖常见崩溃恢复与重试窗口，又不无限保留 | **PENDING_OWNER** |
| 重试 | 出站对 429 / 5xx / 超时 / 网络中断可重试；对 400 / 401 / 403 等契约或权限拒绝，停止对同一非法体的盲目重试并审计。不得为重试而改写租户或身份 | 与 D-07 非阻塞缓冲一致 | 待计划细化，原则建议 |
| 重复提交 | 同一 Tenant + Key 在保留期内重复 POST：返回已接受的幂等成功（建议保持 202 + `duplicate: true`），不创建第二条业务记录 | 支持 at-least-once | 建议保持 |
| 冲突 | 同一 Tenant + Key 但事件身份或关键载荷指纹不一致：建议 **409 Conflict**，不覆盖原记录，不入库新记录 | 防止幂等键被复用到不同事件 | 待签批 |
| 租户隔离 | 只使用已验证 `auth.tenantId`。事件体内 `tenantId` 必须与其相等，否则 403。不得用未验证字段做隔离 | 现有 `tenant_mismatch` 已部分实现 | 待与 D-01/D-02 一并签批 |
| 审计与指标 | 至少计数并审计：接受、幂等命中、409、400/401/403/413/429/503、认证失败、跨租户拒绝、超限拒绝、未知字段拒绝、服务端红化拒绝、授权查询失败。审计不得包含未红化载荷 | 否则无法验收 | 待批 |

## 3. 出站侧配合（建议）

- 超出已批准（或候选待批）体上限时，出站不得截断 payload 再发送；应记失败并按 WAL 规则保留或进入死信 / 拒绝审计。
- 429 / 5xx / 网络中断：由异步缓冲重试；主执行链不等待。
- 400 / 401 / 403 / 409 / 413 中的永久拒绝类错误不得无限重试同一非法体。

---

## 4. 验收条件（建议）

1. GET 不出现在正式 Adapter 契约与跨仓官方测试的成功路径中。
2. 请求中加入未声明字段后，持久化记录中不出现该字段。
3. 超过批准体上限的请求被整体拒绝，数据库无部分记录，响应不是 202。未批准前不得用 64 KiB 宣称生产契约已生效，但可用该候选值设计待批试验。
4. 截断后的半截 JSON 不得被当成成功事件。
5. 相同 Tenant + Key 的重复 POST 不产生第二条事件；不同 Tenant 的相同 Key 互不影响。
6. 以 Trace ID 为幂等键的事件被拒。
7. 客户端仅声明 `redaction.applied=true` 但服务端检测到未红化敏感数据时，请求被拒绝。
8. 限流触发时返回 429 且带 `Retry-After`，被限流请求未入库。数值以签批值为准。

**当前结论：** 可批准方案已形成；**全部数值与原则均未签署**。64 KiB 与限流数字保持候选。实施阻塞。
